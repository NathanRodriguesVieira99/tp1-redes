# Exercício 1 — Runbook por camadas: Internet no Linux

## Enlace

### Comando 1

```bash
ip link
```

**Saída/evidência:**

```text
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
2: eth0@if8: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP mode DEFAULT group default
    link/ether 96:48:20:09:94:83 brd ff:ff:ff:ff:ff:ff link-netnsid 0
```

**Conclusão:** A evidência indica que as interfaces `lo` e `eth0` estão ativas (`UP`). A interface `eth0` possui capacidade de broadcast e multicast e está com o enlace operacional (`LOWER_UP`). O sufixo `@if8` indica que ela está conectada a outra interface de rede virtual no namespace do host Docker.

## Rede (IP)

### Comando 1

```bash
ip addr
```

**Saída/evidência:**

```text
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
       valid_lft forever preferred_lft forever
    inet6 ::1/128 scope host
       valid_lft forever preferred_lft forever
2: eth0@if8: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP group default
    link/ether 96:48:20:09:94:83 brd ff:ff:ff:ff:ff:ff link-netnsid 0
    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0
       valid_lft forever preferred_lft forever
```

**Conclusão:** A interface `eth0` possui o endereço IPv4 `172.17.0.2/16`, com broadcast `172.17.255.255` e escopo global dentro da rede do container. A interface `lo` possui apenas os endereços de loopback `127.0.0.1/8` e `::1/128`. Não foi exibido um endereço IPv6 global ou link-local na `eth0`.

### Comando 2

```bash
ip route
```

**Saída/evidência:**

```text
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.2
```

**Conclusão:** O container possui uma rota default via `172.17.0.1` pela interface `eth0`, permitindo encaminhar tráfego destinado a redes externas. Também possui a rota diretamente conectada `172.17.0.0/16`, usando `172.17.0.2` como endereço de origem.

## Resolução (DNS/hosts)

### Comando 1

```bash
getent hosts example.com
```

**Saída/evidência:**

```text
104.20.23.154   example.com
172.66.147.243  example.com
```

**Conclusão:** A resolução de nomes funcionou: `example.com` foi associado aos endereços IPv4 `104.20.23.154` e `172.66.147.243`. Isso indica que o mecanismo de resolução configurado no container conseguiu consultar e retornar registros para o domínio.

### Comando 2

```bash
cat /etc/resolv.conf
```

**Saída/evidência:**

```text
# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.

nameserver 192.168.65.7

# Based on host file: '/etc/resolv.conf' (legacy)
# Overrides: []
```

**Conclusão:** O container utiliza o servidor DNS `192.168.65.7`, configurado pelo Docker Engine. A resolução observada no comando anterior é compatível com a existência desse nameserver funcional.

## Hipótese e verificação

### Hipótese de camada baixa

- **Hipótese:** A interface ou o enlace de rede do container está indisponível.
- **Evidências:** Refutada. `ip link` mostra `eth0` com `UP` e `LOWER_UP`; `ip -s link` mostra tráfego recebido e transmitido sem erros ou descartes.
- **Verificação:** A rota conectada `172.17.0.0/16` e a rota default via `172.17.0.1` também confirmam que existe conectividade de camada de rede para fora da LAN do container.

### Hipótese de camada alta

- **Hipótese:** O serviço HTTPS ou a resolução do domínio está indisponível.
- **Evidências:** Refutada para `example.com`. `getent hosts` resolveu o domínio, `curl -I` retornou HTTP `200` e `curl -v` confirmou TCP, TLS e HTTP/2 funcionando.
- **Verificação:** O certificado foi validado (`SSL certificate verify ok`) e o servidor respondeu ao método GET com status `200`.
